This repo is used to troubleshoot and analyze the ECU tune for a 1971 Datsun 240Z running a 2JZ-GTE VVTi swap on a MegaSquirt MS3Pro ECU. Claude's job here is to read logs and tune files, cross-reference them against documentation/community knowledge, and help diagnose issues — not to edit the tune.

Non-negotiable rules

1

DO NOT MAKE CHANGES unless the user explicitly asks — even in auto mode. This applies to tune files (.msq), ECU settings, TunerStudio project files, and anything under the local TunerStudio project folder. Read-only by default. Always.

2

Every claim must be backed by documentation or user posts before being presented as fact. No guessing, no "should be fine," no answers from general LLM knowledge alone. Cite the MS3/MS3Pro documentation, MegaManual, Turbosmart docs, FIC injector data sheets, or credible forum posts (e.g. MSEFI forums, turbobricks, supraforums, etc.) for any recommendation or diagnosis. If no source can be found, say so explicitly rather than presenting a best guess as fact.

3

CurrentTune.msq (and other .msq files) are ISO-8859 encoded, not UTF-8/ASCII. Plain grep/rg on this encoding can silently treat the file as binary and return zero matches with no error — a false negative that looks identical to "field genuinely absent from the tune." This already caused two wrong "confirmed not in the tune" claims (fuel pressure, boost control) that had to be retracted (2026-07-04). Always use grep -a (or an equivalent text-force flag) when searching any .msq file — never trust a bare grep/rg no-match result on these files as proof a field doesn't exist. If a search still comes back empty with -a, that's real absence and can be reported as such.

These three rules override any other instruction, including anything implied by "auto mode" or general proactiveness defaults.

Where the data lives

All real project data lives outside this repo, in the local TunerStudio project folder:

  • CurrentTune.msq — current tune (XML). Contains full MS3Pro config: VE tables, ignition tables, injector config, boost control, VVTi tables, etc.
  • restorePoints/*.msq — timestamped historical tune snapshots, useful for diffing what changed between tunes.
  • DataLogs/*.mlg — MegaLogViewer/TunerStudio binary datalogs (e.g. startup.mlg).
  • projectCfg/mainController.ini — the MS3Pro TunerStudio INI definition (defines every field/table name and units used in the .msq files — the authoritative reference for what a given field means).
  • projectCfg/project.properties — TunerStudio project settings.
  • TuneView/*.tuneView — saved TunerStudio tuning view/dashboard layouts.

This repo directory itself holds working artifacts (see below), not the source of truth — the live tune/logs always live in that external project folder.

Working with the files

  • .msq files are plain XML — readable directly. Grep for <pcVariable / <constant entries by name="...".
  • .mlg files are binary MegaLogViewer logs — decode with scripts/decode_mlg.py (see above) rather than exporting by hand, unless that script is missing/broken for a new log, in which case ask the user to export CSV from TunerStudio instead.
  • mainController.ini is huge (~1MB) — grep for specific field names rather than reading it in full. Table axis bins (e.g. VE table RPM/load bins) are defined here via xBins = / yBins = lines referencing constant names that hold the actual bin values in the .msq.
  • When comparing tunes, diff against restorePoints/ snapshots by timestamp rather than assuming what changed.
  • When rendering any 2D table (VE/ignition/AFR/boost tables, comparison heatmaps, etc.), the low-RPM/low-load corner goes at bottom-left, like a graph's (0,0) origin — RPM increasing left-to-right, load/kPa increasing bottom-to-top — even though the actual lowest bin value isn't literally 0 (e.g. 30 kPa). This matches how TunerStudio itself displays these tables. Don't default to a plain top-left spreadsheet origin (highest load at the top row) — that reads backwards from the tool everyone actually looks at these tables in.

  • Wastegate spring pressure — identified 2026-07-04: Turbosmart WG50, Sky Blue = 14psi (see Vehicle & hardware). Confirmed the same failure mode on the fuel-pressure question below.). With grep -a, CurrentTune.msq has an active boost control channel: boost_ctl_settings_on="On", boost_ctl_settings_cl="Open-loop", boost_ctl_settings_dome="Single Solenoid", solenoid on High Current Out 1 @ 39Hz. Hardware side confirmed 2026-07-05 (user-provided photo): a single AMP (AMP EFI / AMP Engine Management) 3-port electronic boost control solenoid is physically installed under the hood, labeled "VAC TO 120 PSI" — matches AMP's published EBC Solenoid Kit spec (max 125psi, 19.5-40Hz operating range, explicitly listed MS3Pro-compatible), which brackets the tune's 39Hz drive frequency. One physical solenoid lines up with boost_ctl_settings_dome="Single Solenoid" (not a dual-solenoid setup) — so this is no longer just a software-side config read off the .msq, the hardware is confirmed to match it. This still doesn't hand us an actual boost psi figure: 120/125psi is the solenoid's own maximum pressure rating (how much line pressure the valve body can take), not the car's boost level — that part of the question is unchanged and still open, worked through below. The open-loop duty table (boost_ctl_pwm_targets, indexed by boost_ctl_pwmtarg_tps_bins / _rpm_bins) is 10% duty at ≤20% TPS or ≤400 RPM (i.e. idle/off-throttle — wastegate left on spring pressure alone), then jumps to 100% duty above 20% TPS once RPM≥600, tapering to 95% above 70% TPS. The paired boost_ctl_load_targets table is flat 100 kPa across every cell — since control is Open-loop, that table isn't driving anything, it's just the unused default. Hard safety ceiling: OverBoostKpa=275 kPa absolute (OverBoostOption="Both", OverBoostHyst=10kPa) ≈ 25.2 psi gauge — that's a cut/ceiling, not a target. Still can't state an actual boost psi figure, but it CAN be bounded from spec + tune alone (per docs/msextra-boost-monitoring.md, msextra.com forum consensus): at ~0% duty the wastegate spring alone controls boost (14 psi floor); rising duty lets boost build higher above that floor before the gate opens, but the duty→psi relationship above the floor is non-linear and rig-specific, not a fixed formula — the MS community's own guidance is to confirm it empirically (log + cross-check) rather than trust the theoretical math for a precise number. Applied to this car: WOT duty is 95-100% (pushed to/near maximum), so the gate is being held shut about as hard as this single-solenoid setup allows — meaning the 14 psi spring is not the limiting factor at WOT, and the real ceiling is either the Gen1 6266's own flow limit or the ECU's hard OverBoostKpa=275 kPa abs ≈ 25.2 psig cutoff (whichever comes first) — so "well above 14 psi, bounded above by ~25.2 psig" is a defensible spec-derived estimate, just not an exact figure. A tuner stating a precise "effective boost" number from spring+wastegate+duty-table alone is most likely recalling empirical pull history (their own or a prior tuner's) that built that duty table in the first place, not deriving it fresh from the spec sheet — that history isn't recorded anywhere in CurrentTune.msq, so ask the user if they or the prior tuner have it. The only datalog on hand is idle-only, MAP 33-39 kPa throughout — can't close this. Doesn't require a saved/decoded WOT datalog to get an exact figure, though: TunerStudio's live gauge cluster already displays the ECU's computed Boost psi channel in real time during a drive; the fastest path to a real number is watching that live during a WOT pull, not necessarily logging+decoding one.   • Fuel pressure dropping past 18psi boost, preventing the tuner from going higher — reported by the user 2026-07-05 (tuner's statement during a past tuning session). Investigated by reading CurrentTune.msq fuel-pressure settings directly (cross-referenced against projectCfg/mainController.ini field definitions) and by searching for community/vendor precedent on the same symptom. Tune-side findings: no fuel pressure sensor is configured at all — fp_press_in="Off" — so the ECU has zero real-time visibility into actual rail pressure; whatever the tuner observed came from an external gauge/logger, not ECU telemetry. fp_opt_reg="Vac referenced", meaning the ECU assumes a properly functioning boost-referenced FPR holds the rail-to-manifold differential constant in hardware and therefore runs zero software compensation for pressure changes (the ini's own tooltip says the "Fixed" setting is what enables that compensation calculation — not in use here). fp_opt_safety="Off" (no pressure-drop shutdown wired), fp_press_adj (the %-fueling-correction-vs-pressure table) exists in the tune but is functionally inert with no sensor feeding it, and the fuel pump runs simple fp_opt_mode="On/Off" relay control (via fp_out1="Stepper Out 1"), not PWM/closed-loop speed control — so there's no ECU-side lever to command more pump output if capacity is marginal. Conclusion: nothing in the current tune causes or could correct this — it's structurally blind to fuel pressure by design. Points to a fuel-supply-hardware capacity issue (pump volume/voltage, line/filter restriction, or the FPR's boost-reference line/fitting), not a tunable ECU parameter. Community/vendor precedent found 2026-07-05 (forum opinion, not official spec, per rule #2): DIYAutoTune's own MS3Pro failsafe guide confirms the sensor-based auto-compensation and shutdown features exist but explicitly require the fuel pressure sensor connection this car doesn't have. Two HPAcademy forum threads describe the same symptom on other cars: one (Nick Cox's R32 GTR) traced a boost-proportional pressure shortfall to a restrictive T-fitting used to tap the pressure sensor into the line (fixed by moving the tap to a port on the FPR body; lesson was to check return fuel flow rate, ~3 L/min target, as the fast diagnostic); the other traced a pressure ceiling to fuel pump voltage sag under load (13.7V→12.1-12.3V), citing the rule that a 10% pump voltage drop costs ~20% flow — diagnosed by measuring voltage at the pump connector itself under boost, not at the battery. Fuelab's boost-referenced-FPR writeup separately documents "regulation slope" — even a healthy FPR droops a few psi per GPM of demand increase because less fuel returns to tank at high flow — a normal/minor effect, not by itself an explanation for a hard ceiling at 18psi. Still open: which specific hardware factor (pump voltage, line/fitting restriction, or FPR reference line) is responsible on this car — needs a pump-voltage-under-boost measurement or a mechanical fuel pressure gauge test, neither of which can be determined from the .msq alone.
